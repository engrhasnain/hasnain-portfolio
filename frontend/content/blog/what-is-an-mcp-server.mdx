Most AI assistants can talk about your business. Very few can *do* anything in it. They can't look up a customer, check a booking or create an invoice, because they have no safe way to reach the systems where that work happens.

The **Model Context Protocol (MCP)** fixes that. It is an open standard, started by Anthropic, for connecting AI models to tools and data. An **MCP server** is the piece you build for your own system.

## MCP in one paragraph

An MCP server sits between the AI and one of your systems (a CRM, a database, a file store, an internal API). It tells the AI which **tools** exist, such as `find_customer` or `create_booking`, what each tool does and what input it needs. When the model decides to use a tool, the server checks the request, runs it against the real system, and returns the result.

The model never gets your database password. It only gets the tools you chose to give it.

## Why not just write an API integration?

You can, and for one app talking to one system that is often fine. MCP starts to pay off when:

- **More than one AI client needs the same access.** Claude Desktop, Claude Code and your own agent can all use one MCP server.
- **You have many systems.** I built the MCP layer of an [AI operations platform](/projects/ai-operations-platform): 6 servers, 17 MCPs and over 1,000 tools. Without one standard pattern for every tool, that would be unmanageable.
- **You need control.** Permissions, input validation and audit logs live in one place, on the server, instead of being scattered through prompts.

## What a good MCP server looks like

1. **Small, clear tools.** `get_invoice(invoice_id)` beats `do_billing_stuff(query)`. The model picks tools by reading their names and descriptions, so write them for a reader.
2. **Strict input schemas.** Reject bad input before it touches a real system.
3. **Read and write kept apart.** Reading data is low risk. Changing data should need the right permission, and sometimes a human's approval.
4. **Logs for every call.** When something looks wrong, you should be able to see exactly which tool ran, with what input, for whom.

## When you don't need one

If your AI only answers questions from documents, you need a good RAG chatbot, not MCP. If you have one simple automation, an n8n workflow may be faster to ship. MCP is for when the AI has to work with your systems again and again, across tools and teams.

## The short version

An MCP server turns "the AI knows about our business" into "the AI can work in our business, within limits we set". If that is the step you are trying to take, it is worth building properly.
