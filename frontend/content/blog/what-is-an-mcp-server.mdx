Most AI assistants can talk about your business. Very few can *do* anything in it. They can't look up a customer, check a booking or create an invoice, because they have no safe way to reach the systems where that work happens.

That is changing fast. More teams want Claude, or their own AI agent, to work inside the CRM, the database and the internal tools, not just next to them. The real question is how to let it in without handing over the keys to everything.

## What an MCP server is

The **Model Context Protocol (MCP)** is an open standard for connecting AI models to tools and data. Anthropic introduced it in November 2024, and it is now supported far beyond Claude. ([Anthropic's announcement](https://www.anthropic.com/news/model-context-protocol))

An **MCP server** is the piece you build for one of your own systems: a CRM, a database, a file store or an internal API. It sits between the AI and that system, and it tells the AI which **tools** exist, such as `find_customer` or `create_booking`, what each tool does, and what input it needs. When the model decides to use a tool, the server checks the request, runs it against the real system and returns the result. ([MCP specification: tools](https://modelcontextprotocol.io/specification/latest/server/tools))

Think of it as a menu of approved actions. The model never gets your database password. It only gets the tools you chose to give it.

## Why it matters for your business

Here is what that looks like in practice. A sales lead asks Claude: "Which deals haven't been touched in two weeks?" With an MCP server for the CRM, Claude calls a tool like `list_deals(stale_days=14)` and answers with real data. Without it, the model can only guess, or someone has to export a spreadsheet first.

You can connect an AI to a system with a one-off API integration, and for one app talking to one system that is often fine. MCP starts to pay off when:

- **More than one AI client needs the same access.** Claude Desktop, Claude Code and your own agent can all use one MCP server, instead of three separate integrations.
- **You have many systems.** Every tool follows the same pattern, so the tenth integration is as easy to review as the first.
- **You need control.** Permissions, input checks and logs live in one place, on the server, instead of being scattered through prompts.

That last point matters most. The real risk with an AI that can act is rarely the model. It's the access around it. OWASP, the security community behind the best-known list of risks for AI applications, has a name for it: [excessive agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/). It means an AI with too many tools, too many permissions, or too much freedom to act without a person.

## How I build an MCP server

1. **Small, clear tools.** `get_invoice(invoice_id)` beats `do_billing_stuff(query)`. The model picks tools by reading their names and descriptions, so I write them for a reader, not for myself.
2. **Strict input schemas.** Every tool declares exactly what input it accepts. Bad input is rejected before it touches a real system.
3. **Read and write kept apart.** Reading data is low risk. Changing data needs the right permission, and anything public or hard to undo waits for a person to approve it.
4. **Proper sign-in.** Remote MCP servers are protected with OAuth, the authorization method the [MCP specification](https://modelcontextprotocol.io/specification/latest/basic/authorization) describes, so each client only gets the access it was granted.
5. **Logs for every call.** When something looks wrong, you can see exactly which tool ran, with what input, for whom.

<Callout>

**From a real build:** I built the MCP layer of an [AI operations platform](/projects/ai-operations-platform) for a digital marketing agency: 6 servers, 17 MCPs and over 1,000 tools that Claude can use. The MCP servers are protected with OAuth 2.1, and anything that goes live waits for a person to approve it. Without one standard pattern for every tool, a layer that size would be impossible to review.

</Callout>

## When you don't need one

If your AI only answers questions from documents, you need a good [RAG chatbot](/blog/rag-chatbots-that-dont-make-things-up), not MCP. If you have one simple automation with one fixed step, an n8n workflow may be faster to ship. And if nobody will look after the server once it's live, wait: an MCP server is a small piece of software, and it needs an owner like any other.

MCP is for when the AI has to work with your systems again and again, across tools and teams.

## The short version

An MCP server turns "the AI knows about our business" into "the AI can work in our business, within limits we set". Keep the tools small, keep reading and writing apart, and keep a person in the loop for anything that can't be undone.
