## The problem

A new contractor website needs copy for every page, section and element: headlines, service descriptions, FAQs and calls to action. The service pages repeat for each service the business offers. Writing all of that one prompt at a time takes days, and a model with no context writes copy that could belong to any company. Big runs also break halfway. A deploy restarts the server or a vendor rejects a batch, and someone has to work out what was already done.

## What I built

- **A spreadsheet of prompts.** Admins upload an .xlsx file with page type, section, section piece and prompt, and each row becomes a template for every future run.
- **Client grounding with RAG.** Each client's geography, company overview answers, topical maps and service Q&As are chunked, embedded with OpenAI text-embedding-3-small and stored as 1536-dimension vectors in pgvector. Each request pulls the closest chunks from every source by cosine distance.
- **Two batch providers.** Requests go to Anthropic Message Batches, or to the OpenAI Batch API as an uploaded JSONL file, with the provider and model chosen per run. One general batch covers the shared pages, and every service category gets its own batch of service page templates.
- **Checkpoint and resume.** The run record keeps the submitted batch IDs and the last processed index. A resume call continues from that checkpoint instead of starting again.
- **Saved on shutdown.** On SIGTERM or SIGINT, the checkpoint of every active run is written to the database before the process exits.
- **A second pass inside every prompt.** A review prompt from the shared prompt library is added to each request, so the model checks its draft against the review rules before it returns JSON with the content and a short analysis note.
- **Q&A generation on BullMQ.** Service Q&As run as a background job that sends one Claude batch request per service category, while a Socket.IO channel pushes live progress to the portal.

A run will not start until the client's embeddings exist, so every prompt is grounded in that client's own data. Each request carries a custom ID that encodes its template and its category, which is how a result finds its slot when the batch comes back hours later. A concurrency limit caps how many batches are in flight, a sliding-window rate limiter paces the embedding calls, and a failed submission is retried with a growing delay. A batch that fails outright is recorded on the run, and it can be resubmitted on its own without touching the batches that succeeded.

## Built to be trusted

- **Locked-down routes.** Content routes sit behind JWT authentication and an admin guard, Q&A routes behind JWT and a permissions guard, and the progress socket drops any connection without a valid token.
- **No double processing.** The Q&A worker logs each batch it processes, so a status check that runs again skips anything already saved.
- **Progress that survives a refresh.** The portal never polls. When a browser reconnects mid-run, the socket replays the current progress snapshot.
- **No filler.** When the model answers with its no-content marker, the slot is saved empty with the model's note instead of invented copy.
- **Traceable outputs.** Every saved output keeps the prompt that produced it, its analysis note, and its input and output token counts.

## By the numbers

- 35 API routes: 23 for website content and 12 for Q&A generation
- 5 client data sources indexed into one pgvector table
- 1536-dimension embeddings from text-embedding-3-small
- 2 batch providers: Anthropic Message Batches and the OpenAI Batch API
- Q&A batch status checked every 5 minutes, for up to 144 checks
