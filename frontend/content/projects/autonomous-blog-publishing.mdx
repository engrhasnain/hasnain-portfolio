## The problem

Each client business needs a steady flow of useful blog posts on topics people in its area actually search for. Doing that by hand across a whole fleet of WordPress sites means picking topics, writing, formatting, uploading, and then checking that each post went live and got indexed. Miss a step and a post sits unpublished, goes out twice, or never reaches Google.

## What I built

- **Five topic engines.** A Search Console gap miner, auto-discovery, a seasonal calendar, a location by service grid and DataForSEO long-tail research all feed the topic list.
- **A writer, a validator and a renderer.** Claude writes the post, a validator checks it, and a Gutenberg renderer turns it into native WordPress blocks.
- **A plan, fire and layout orchestrator.** Every 5 minutes it spreads the day's posts across enabled client sites (the one that has gone longest without a post goes first), fires the posts that are due, and installs the blog layout where it is missing.
- **Publishing with proof.** Posts go out through the WordPress REST API and SSH, and the system then reads the live page back instead of trusting the response.
- **Indexing follow-up.** IndexNow is rolled out across the fleet, and an indexing queue follows up on each new post after it is published.
- **Search tools for Claude.** An MCP server gives Claude 56 search tools, from batch URL inspection and cannibalization checks to IndexNow submission, so Claude can work from the same search data as the pipeline.

The orchestrator runs on a schedule with no one pressing a button. Each post moves through planning, writing, images, metadata, assembly, validation and publishing as tracked states, so it is always clear where a post is and what it is waiting for. After it goes live, the post is read back from the real page and handed to the indexing queue.

## Built to be trusted

- **No double posts.** A post is claimed with a single atomic UPDATE that re-checks its status, so two runs can never grab the same row.
- **One write per site.** Only one post is written to a site at a time, under a fleet-wide concurrency cap, so writes to one site never overlap.
- **Spend caps.** Caps are set per client and for the whole fleet. At 80% of a cap the system raises a warning, and at 100% it blocks new work. The cap is checked every time a post is fired.
- **A sweeper for stuck pipelines.** If the server restarts mid-post, the stranded post goes back in the queue. After a set number of retries it is marked failed for a person to review, so a broken post cannot loop forever.
- **Read-back, not hope.** A post counts as published only once the live page has been fetched and checked.

## By the numbers

- 112 API routes: blog 86, indexing 11, IndexNow 15.
- 72 blog service modules and 12 scheduled jobs.
- 56 MCP search tools for Claude: 22 for Search Console, CrUX and PageSpeed, 25 for indexing and IndexNow, and 9 keyword tools.
- 5 topic engines feeding one publishing pipeline.
