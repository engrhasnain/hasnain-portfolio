## The problem

The agency's clients keep their real work in their own tools: jobs in Housecall Pro or Jobber, books in QuickBooks or a desktop copy of Sage 50, photos in CompanyCam, years of estimates in Google Drive. That record is the best proof of what each contractor does and where. Copying it by hand was slow, and every system has its own traps: auth errors that come back as HTTP 200, photo links that expire within the hour, and customer names and phone numbers that must never reach marketing content.

## What I built

- **Read-only connectors.** Each system gets its own client with token refresh, rate limit backoff and sync state, and none of them writes back to the vendor.
- **A desktop sync agent for Sage 50.** A signed Windows program reads the books through ODBC on the client's own PC every hour and sends them in batches. An interrupted run resumes from its progress file, and every write is an upsert on Sage's internal record key, so a resent batch changes nothing.
- **A receipt per batch, counted back.** After each batch lands, the server runs a COUNT(*) inside the same transaction and returns it in the receipt. A run fails on a count mismatch, a failed verify pass or any rejected record.
- **A document extractor.** It reads files the other readers cannot, such as Apple Pages, ClarisWorks and old Mac files with no extension, and finds invoice fields and inspection findings. Each document is sorted as complete, partial, needs AI or empty, and only scans and photos go to Claude.
- **A project reconciliation workbench.** It gathers job evidence from 12 sources and scores every fragment against a candidate project. Strong matches attach, weaker ones wait as candidates, and a person confirms, rejects or merges.
- **Data browsers and drill-down analytics.** The portal has a screen for each connector with searchable record tables, a raw record panel and a run log. On the analysis tab, any bar, month, town or number opens the records behind it.

Every sync job runs on a schedule behind a Redis lock, so two workers never run the same pull. Housecall Pro and Jobber webhooks are checked against their HMAC signatures, answered at once and processed in the background. Each source reports "not connected" apart from "connected but empty", so a client with no Jobber account never reads as a client with no jobs. Nothing a sync infers, such as a new town or a missing service, goes straight onto a client's profile. It becomes a proposal that a person approves.

## Built to be trusted

- **A PII boundary before the insert.** Jobber queries ask only for allowed fields, an allow-list per entity builds each row, and a scan for the shapes of emails, phones, addresses and card numbers refuses the row. QuickBooks rows pass the same last two gates. A refusal is counted on the run, not hidden.
- **Sage reads, nothing more.** The agent asks only for approved fields, refuses to send anything that looks like payroll, bank, tax or card data, and the server rejects such a field if it arrives anyway. Secrets sit in Windows DPAPI, unsigned updates are refused, and content work sees only cities, ZIP codes, counts and service mix.
- **Photos held until screened.** A customer photo stays unpublishable until face and number plate checks clear it, and an exterior shot that might show a house number goes to a person.
- **Reads that cannot hang the API.** Each document is read in its own child process with a time limit and a memory cap, so one bad file fails alone.
- **Decisions that stick.** A confirmation a person makes is never undone by the next re-scan, auto-merge is switched off, and every decision is logged.
