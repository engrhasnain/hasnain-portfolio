## The problem

One [MCP server](/blog/what-is-an-mcp-server) with ten tools is easy to keep tidy. Three servers with more than a thousand tools are not. Without shared rules, every tool names things its own way, handles errors differently and logs, or forgets to. The model starts guessing, a slow call runs twice, or a destructive action goes through with nobody checking. A contractor marketing agency needed its MCP layer to behave like production software, not a pile of scripts.

## What I built

- **Three production servers.** A client-operations hub with 868 tools, 113 of them generated from a JSON manifest, the [WordPress fleet server](/projects/wordpress-fleet-mcp) with 201 and the [hosting server](/projects/hosting-ops-mcp) with 117.
- **One written standard.** An internal MCP server standard sets the rules for all three: `<prefix>_<resource>_<verb>` names, an always-loaded core of 8 to 12 tools, pagination and field trimming, bulk variants, a health tool and backoff.
- **Two-layer auth.** A bearer gate decides who may call the server at all. The upstream credentials for each system stay on the server and are never handed to the model.
- **A shared tool registrar.** In the hub, tools register through one place that adds request IDs, time budgets, call logs and rate limits to every call.
- **A stable prompt prefix.** The 11 core tools register first, so the start of the tool list stays the same and the cached prompt prefix keeps working.
- **Safe renames.** 24 legacy aliases let tools move to a new prefix without breaking older clients.
- **Honest errors.** Upstream errors are passed through word for word, and the standard sets clear rules for cost and caching.

Claude signs in to the hub through self-hosted OAuth 2.1, with dynamic client registration turned off. Every call gets a request_id and a time budget, with a longer budget for a known list of long-running tools. A sliding-window limit allows 120 calls a minute per tool. Writes are relayed to the platform's Python and Node backend APIs. Each call then lands in a structured log, with secrets scrubbed and tokens and cost tracked. The hub runs FastMCP 2.14 over SSE, with PostgreSQL through asyncpg and SQLAlchemy, S3 and Playwright, in Docker behind nginx on AWS EC2 and Cloudflare, plus six background schedulers.

## Built to be trusted

Each tool is scoped the way I would write an [AI agent's job description](/blog/ai-agent-job-description): what it may read, what it may change, and what needs a person.

- **Destructive tools are marked.** 325 tools carry a destructive flag, and the standard asks for confirmation before any destructive action.
- **Audit by default.** Every call writes a structured log entry with its request_id, cleaned of secrets, along with token and cost tracking.
- **A worked example: domains.** The 21 domain tools make live writes only behind an environment flag. The account balance must cover a whole renewal batch, or nothing renews. Requests to lift a domain lock, fetch an auth code or reactivate a domain go to a human decision queue.
- **No silent DNS damage.** A DNS change that would remove MX records is refused unless it is confirmed. Sync and sweep support dry_run, and every call is written to a write log and read back.

## By the numbers

- 3 production MCP servers with 1,186 tools: 868, 201 and 117.
- 113 hub tools generated from a JSON manifest, and 325 tools flagged as destructive.
- 11 core tools registered first, 24 legacy aliases and 6 background schedulers.
- About 222k lines of Python and 4,461 test functions across the three servers.
